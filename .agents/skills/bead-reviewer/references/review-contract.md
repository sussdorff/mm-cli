# Live Bead Review Contract

## Profiles

- `formal`: layered-contract fields, observable Acceptance Criteria, Means of
  Compliance, Context Pointers, and dependency facts. Work size is not a criterion.
- `semantic`: completeness, consistency, clarity, cohesion, YAGNI, contradictions,
  and ADR compatibility.
- `repository`: current code and test boundaries, cited files and symbols, existing
  helpers, architectural facts, and feasibility.
- `related-beads`: duplicates, overlap, artificial splits, conflicting assumptions,
  blockers, and already-delivered scope.
- `full`: all four profiles.

Repository and related-work inspection must stay bounded by Context Pointers, cited
identifiers, dependency edges, and evidence needed to confirm or reject a claim.

## Result

Return one JSON object:

```json
{
  "bead_id": "clc-example",
  "profile": "full",
  "reviewed_digest": "<sha256>",
  "reviewer_sha": "<sha256>",
  "contract_sha": "<sha256>",
  "outcome": "clean|warnings|blocked|unavailable",
  "unavailable_reason": null,
  "criteria": [
    {"criterion": "formal", "status": "ran|skipped|unavailable", "reason": null}
  ],
  "findings": [
    {
      "rule_id": "REPO-PATH-STALE",
      "finding_id": "REPO-PATH-STALE:clc-example:4b09e7fcff02",
      "criterion": "repository",
      "severity": "blocking|warning",
      "message": "<finding>",
      "evidence": ["relative/path:line", "bead:clc-related"],
      "recommended_change": {
        "operation": "replace|remove|add",
        "target": "<authoritative field, section, or quoted passage>",
        "result": "<exact resulting text or unambiguous resulting constraint>"
      }
    }
  ]
}
```

Every non-unavailable finding carries two separate identities:

- `rule_id` is the stable aggregation key. It must be uppercase kebab case and
  must exist either in the fully resolved hygiene contract or in
  `finding-rule-registry.json`.
- `finding_id` is the occurrence key generated by `finding_rules.py build` from
  `rule_id`, bead ID, criterion, and sorted unique evidence anchors. It is never
  authored as a free-form slug.

Use `ADHOC-UNCLASSIFIED` when a demonstrated finding has no registered rule. This
makes taxonomy debt countable without allowing reviewers to mint incompatible IDs.
Identical canonical inputs describe one occurrence and must be merged. Separate
findings need occurrence-specific evidence anchors. Duplicate or non-deterministic
finding IDs are invalid. Message and recommendation wording are not identity inputs.

`clean` has no findings. `warnings` has at least one finding and only warning
findings. `blocked` has at least one blocking finding. A warning is recorded in the
readiness metadata but does not require repair or human adjudication. A dispute is
caller-owned lifecycle state after author adjudication and is never a reviewer
outcome. `unavailable` reports a missing or wrong repository binding before review;
it requires `unavailable_reason`, an empty or absent digest, and empty `criteria` and
`findings`. All digest validation is skipped because no live artifact was loaded.
`unavailable` never authorizes readiness; the caller must stop or map it to a typed
execution failure, and it must never be persisted in `metadata.review`.

`recommended_change` is an edit instruction, not a suggestion to append review
history. It names the current authoritative target and the state that must exist after
the edit. For `remove`, `result` states explicitly that the target is absent and whether
any replacement remains. Findings such as "clarify this", "address the warning", or
"append a Reviewer-Fix note" are contract-invalid.
